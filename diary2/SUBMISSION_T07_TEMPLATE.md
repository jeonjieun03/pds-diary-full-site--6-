## 인증 구현 설명서

### ② 왜 그걸 골랐나
- 과제 6에서 이미 Supabase(Postgres)를 서버 데이터베이스로 쓰고 있어서, 같은 프로젝트 안의 인증
  기능을 그대로 쓰면 새 서버나 새 서비스를 추가하지 않아도 됩니다.
- 비밀번호를 우리 코드가 직접 만지지 않고 Supabase의 GoTrue가 대신 해시·보관해 주므로,
  비밀번호 취급 실수(평문 저장, 약한 해시 등)의 위험을 줄일 수 있습니다.

**검토했지만 고르지 않은 방법**
- 직접 구현(bcrypt + JWT): 비밀번호 해시, 토큰 발급·검증·만료, 재설정 흐름까지 전부 스스로
  구현하고 지켜야 해서, 6~8시간 계획 시간 안에 안전하게 만들기엔 위험이 크다고 판단해 제외했습니다.
- Passport.js 등 Node 서버 기반 라이브러리: 이 앱은 GitHub Pages(정적 호스팅)로 배포되어
  Node 서버 자체가 없으므로 애초에 쓸 수 없습니다.

### ③ 어디를 어떻게 고쳤나
과제 6과 같은 Supabase 프로젝트를 쓰지만, 표는 완전히 분리했습니다(`plans_t07`처럼 이름 끝에
`_t07`이 붙은 새 표). Supabase 무료 요금제가 프로젝트를 2개까지만 허용하고 과제 8에서 새
프로젝트가 하나 더 필요해서, 새 프로젝트를 만드는 대신 같은 프로젝트 안에 표만 새로 팠습니다.
과제 6이 쓰는 원본 표(`plans` 등)와 그 정책은 전혀 건드리지 않아, 과제 6 결과물 주소는 이
작업과 무관하게 로그인 없이 그대로 열립니다.

### ⑥ 아직 못 막은 것
- **로그아웃해도 이미 발급된 access token은 자기 만료 시각까지 유효함**: GoTrue의 access token은
  상태를 갖지 않는 JWT라서, 로그아웃은 refresh token만 서버에서 폐기하고 access token 자체를 즉시
  무효화하지는 못합니다. 기본 만료(1시간) 전까지는, 만약 그 토큰이 유출되었다면 로그아웃 이후에도
  잠깐은 쓰일 수 있습니다.
- **무차별 대입(브루트포스) 로그인 방어를 앱 차원에서 따로 걸지 않음**: 연속 실패에 대한 잠금/지연
  로직이 없고, Supabase 프로젝트의 기본 요청 제한(rate limit)에만 의존하고 있습니다.
- **비밀번호 재설정(이메일로 링크 보내기) 화면이 없음**: 비밀번호를 잊으면 현재는 복구할 방법이
  없습니다.
- **2단계 인증이 없음**.
- **로그인 시도/실패에 대한 별도 감사 로그를 앱에서 남기지 않음**(Supabase 대시보드의 기본 로그에만
  의존).
